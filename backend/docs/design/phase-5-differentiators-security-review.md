# Security Review - Hash-Chained Ledger, Drift Detector, Self-Hosted Governance, Content-Classification Routing, Shadow AI Discovery

Scope reviewed: services/{audit,audit_chain,compliance_settings,drift_detector,self_hosted_providers,dlp,content_classifiers,model_policy,shadow_ai,budget}.py, api/deps.py's new require_shadow_ai_ingest_token, api/v1/shadow_ai_ingest.py, api/v1/admin/{audit_chain,drift_detector,self_hosted_providers,sensitivity_label_mappings,shadow_ai}.py, api/v1/gateway/{chat,common}.py's Phase 5 additions, migrations 0037-0043, docs/policy/shadow-ai-data-handling.md, main.py's Phase 5 wiring, and the corresponding frontend admin console screens.

This review ran after a QA pass had already found and routed back 3 real issues (1 security-blocking, 1 functional, 1 encryption-at-rest gap). All 3 were fixed by backend-developer before this review began; this review independently re-verified each fix by direct code reading and by running the relevant regression tests itself, not by trusting the fix report.

## Findings - fixed before/during this review (independently re-verified, not trusted from the fix report)

1. (Blocking, fixed, verified) Sensitivity-label DLP bypass for financial_data. services/dlp.py::scan_texts() computes financial_data_needed from whether content-aware categories are enabled, with no subtraction of skip_categories (the sensitivity-label short-circuit mechanism) - confirmed by direct code read. skip_categories now only narrows the source_code/legal classification signal (which have no DLP redact/block action), never the DLP entity scan itself. Verified the legitimate half still works: the classification/routing signal is still correctly short-circuited for a pretrusted label (ORed directly into category_findings at the gateway-pipeline layer, independent of whether the underlying scan also found it) while the DLP scan itself always runs regardless of any label. Ran tests/integration/test_sensitivity_label_financial_data_dlp_bypass.py directly - passed, proving a real IBAN is blocked both with and without the pretrusted label present.

2. (Functional, fixed, spot-verified) Drift detector self-hosted canary gap. services/drift_detector.py now reads the SAME pre-warmed self-hosted model route cache instance the real gateway path reads (not a second, independently-derived one), falls back to it when a canary target isn't in the static model registry, fetches the self-hosted credential via the same decrypt path the real gateway uses, and computes cost via the self-hosted cost formula (never the normal per-token pricing path or the real budget-charging function). Ran the regression test directly - passed.

3. (Blocking, fixed, verified) shadow_ai_ingest_config.webhook_url plaintext-at-rest. A new migration drops the plaintext webhook_url column and adds an AES-256-GCM ciphertext/nonce/auth_tag envelope, reusing the exact same shared encrypt/decrypt helper functions the codebase already uses for Team.webhook_url and provider keys - no new crypto code. Confirmed genuine end-to-end wiring, not a half-migrated state: the config-write path encrypts via the real shared helper, uses a distinct AAD from the team-webhook encryption, the only place plaintext is ever reconstructed is in-memory immediately before an outbound webhook delivery call, and no lingering plaintext column or reference exists anywhere in the codebase (grepped the whole source tree). GET responses expose only a webhook_configured boolean, never the URL or ciphertext. The policy doc's own disclosure of this gap has been updated to describe the fixed state.

## Verified - no new issues found

- Hash-chain forgery/tamper detection is real (5.2). The verification endpoint recomputes each row's chain_hash from that row's own stored fields via the exact same function used at write-time and backfill-time (one shared, dependency-free module - no risk of write-time and verify-time formulas silently diverging), and independently checks the stored prev_hash against the immediately-preceding row's stored chain_hash. A raw-SQL UPDATE to a historical row bypassing the service layer entirely is caught by the verification endpoint, naming the exact entry id and chain_seq - proven by a real integration test, not just code inspection.
- Hash-chain reordering is caught. Swapping two rows' chain_seq values (leaving chain_hash/prev_hash untouched) breaks the prev-hash linkage check for whichever row now walks immediately after the swap point, regardless of which two rows are involved - verified by manual trace of the verification algorithm.
- Hash-chain write concurrency is genuinely serialized. write_audit_entry takes a row lock on the org's compliance_settings row (guaranteed to exist before chaining can be enabled) before reading the chain tail and inserting, preventing two concurrent writes from forking the chain. Proven under real concurrent load (8 parallel writes) with no fork detected.
- Backfill atomicity holds. The one-time historical backfill runs inside the same locked transaction as the enable-toggle, never releasing the lock between batches.
- Content-classification's multi-category intersection logic correctly degenerates to the pre-Phase-5 single-PII-check behavior for a PII-only finding, and correctly produces an empty-intersection block for a disjoint multi-category configuration - verified via direct test runs, not just code reading.
- Shadow AI's ingestion-token trust boundary is genuinely isolated in both directions. The new auth dependency shares no code path with any existing admin/gateway/SCIM auth check, uses constant-time hash comparison, and fails closed when no token is configured. The ingestion route's auth dependency is declared on the route itself, not inherited from a router-level dependency that could accidentally also gate other endpoints, and is registered as a genuinely separate router in the app. Reverse-isolation is proven by real tests: the ingest token cannot authenticate to any admin-gated endpoint or the gateway chat endpoint; the admin break-glass token and a real service-account key cannot authenticate to the ingest endpoint.
- Shadow AI's data-minimization gate is structural, not just policy. Only rows whose destination host matches a curated, admin-managed allowlist are ever persisted from an ingested batch; everything else is dropped in-memory before touching the database session, never logged even at debug level. The event table's schema has no column capable of holding a full URL, query string, or request/response body at all.
- Shadow AI's retention purge job is genuinely wired into the scheduler's tick sequence, not dead code.
- Shadow AI's Team Lead report scoping is enforced server-side. The report endpoint forces the caller's own actual led-team-ids; a client-supplied team filter for a team the caller doesn't lead is rejected, never silently widened or ignored.
- Self-hosted provider credential encryption uses a genuinely distinct AAD binding from BYOK provider keys, so a ciphertext could not be successfully decrypted if swapped between the two tables even within the same org. The self-hosted cost estimate is confined entirely to the same cost_usd column real provider costs use (so budgets/dashboards work unmodified) with no path to being silently treated as more authoritative than its documented "estimated" label - the drift detector's canary cost for self-hosted models is similarly confined to the canary-only cost column, never touching real budget figures.
- RBAC boundaries hold on every spot-checked new admin endpoint across all five sub-features, matching the design doc's intended role assignments exactly (verified by reading the actual dependency-injection wiring, not just endpoint names/docstrings).
- Audit trail integrity for Phase 5's new event types is preserved - every new audit action is written from server-derived data only (row ids, server-read status), never a client-controlled field.
- A sensitivity label mapped to the pii category is correctly a no-op for DLP purposes - PII's own detector toggles are driven purely by the existing DLP policy configuration, never gated by the new short-circuit mechanism at all.

## Flagged, not blocking - needs follow-up or the deploying operator's attention

1. Hash-chain tail truncation is not detectable by the verification endpoint. If someone with raw database write access (bypassing the application layer entirely) deletes the highest-chain_seq row(s) - chopping off the tail rather than tampering with a row in the middle - verification walks whatever rows remain, finds them fully internally consistent, and reports the chain as intact with a smaller but plausible-looking entry count. There is no independently-persisted "expected latest position" anywhere outside the audit table itself. This is the classic weakness of a hash chain without external anchoring, and is not a regression or an unaddressed requirement - the phase's own resolved scope explicitly defers external anchoring/timestamping to a fast-follow, and this trade-off is already listed as an accepted v1 limitation. What's missing is explicit disclosure of the concrete consequence ("verify cannot detect a deleted tail") in the admin UI's help text and in this project's own known-limitations documentation, so an Org Admin doesn't over-trust an "intact" verification result against a truncation attack specifically. Recommend adding that one sentence of disclosure; not a re-review gate.
2. A per-self-hosted-endpoint usage/cost breakdown endpoint named in the technical design's API-contract table was not built - the admin console instead shows an org-wide aggregate for all self-hosted traffic combined, clearly labeled as such. This is a functional completeness gap, self-disclosed in both the code and the UI, not a security issue (no data leak, no RBAC gap). Track as a fast-follow.
3. Shadow AI's optional free-form metadata field accepted at ingestion time has no size or content-shape limit enforced at the schema level, unlike every other field on that endpoint. The primary data-minimization control (the hostname allowlist gate) is unaffected by this, and exploiting it requires already holding a valid, org-issued ingestion credential - but the "connection metadata only" claim in the data-handling policy is, for this one field, a documented convention rather than a technically enforced one. Recommend adding a small size cap (a few KB) in a future pass so the claim is enforced, not just documented. Low severity, not blocking.
4. Everything already flagged in the Phase 4 security review (pricing-table live verification, tokens_per_min enforcement gap, a from-scratch docker-compose pass on the operator's own machine, Vertex AI streaming-usage accuracy) remains an open operator-facing item, unchanged by this phase.

## Sign-off

PASS. All three QA-identified issues are correctly and completely fixed, independently re-verified by direct code reading and by running the specific regression tests - not by trusting the fix report. The financial_data DLP-bypass fix genuinely closes the gap without breaking the legitimate sensitivity-label short-circuit for source_code/legal. The drift-detector self-hosted canary gap now reuses the exact same warmed route cache the live gateway path uses. The shadow-AI webhook URL is now genuinely encrypted at rest with no lingering plaintext, using the codebase's existing shared encryption helpers, never echoed on any read path.

The hash-chained audit ledger's tamper-evidence guarantee holds up under direct scrutiny: forgery of a single field is caught by hash recomputation, reordering is caught by the prev-hash linkage check, and concurrent writes are genuinely serialized. The one real gap - tail truncation is undetectable by design without external anchoring - is a pre-existing, explicitly-scoped-out limitation of the v1 design, not a regression or an unmet requirement; flagged for a documentation fix, not blocking.

The shadow-AI ingestion token is a genuinely fourth, non-overlapping trust boundary in both directions. RBAC boundaries hold on every spot-checked new admin endpoint across all five sub-features, including server-side-enforced Team Lead scoping on the shadow-AI report. Self-hosted credential encryption uses a genuinely distinct AAD binding from BYOK provider keys, and the self-hosted cost estimate is correctly confined with no path to being treated as more authoritative than its documented label.

Test baseline reproduced independently: 754 passed / 1 skipped (unit), 225 passed / 3 skipped (integration, run against a live Postgres and live Redis - the skips are genuinely Redis-gated tests self-skipping cleanly for an unrelated reason). Phase 5 is approved to ship, contingent on tracking the truncation-detection disclosure and the metadata size cap above as fast-follows, neither of which is a re-review gate.
