# Security Review - Multi-Key Failover, Rate Limiting, Caching, Graceful Degradation

Scope reviewed: everything added in Phase 4 - services/{provider_key_health,provider_keys,rate_limit,response_cache,degradation}.py, gateway pipeline integration in api/v1/gateway/{common,chat,completions,embeddings}.py, new admin routers (api/v1/admin/{rate_limits,caching_settings,degradation_policy,backup_groups,failover_events,degradation_events,cache_admin,provider_key_health,failover_override}.py), schema/migrations 0023-0036, the warmed process-level config caches (RateLimitCache/CachingSettingsCache/DegradationPolicyCache) wired into main.py lifespan, and the corresponding frontend admin console screens.

This review ran in two passes: a full initial review (found 3 blocking issues) and a targeted re-verification pass after backend-developer fix round (confirmed all 3 fixed, reviewed the one new admin endpoint added during the fix round). Both passes are consolidated here.

## Findings - fixed during this review

1. (Blocking, fixed) Cache hits bypassed residency/DLP re-validation - a policy tightened after a cache write was never re-checked on a subsequent hit. check_response_cache() in api/v1/gateway/common.py returns a cache HIT before check_residency()/run_dlp_scan() ever run. Residency/DLP policy can change after a cache write, and cache TTL can be up to 24h (cache_ttl_minutes max 1440) - a response cached under a permissive policy could have been served for up to 24h after an Org Admin tightened residency/DLP policy to forbid it, violating AC4.3.6's guarantee that a cached response is never served across a policy boundary. Fixed by wiring cache invalidation (CacheInvalidator.clear_team/clear_all) into every residency/DLP policy write path (services/residency.py set_org_residency_rule/set_team_residency_rule/delete_org_residency_rule/delete_team_residency_rule, and services/dlp.py set_dlp_policy/set_team_dlp_override plus the custom-DLP-pattern router handlers in api/v1/admin/dlp_policy.py). Verified in the re-review: invalidation fires after session.commit() on every path (no race window), fails open on Redis unavailability (never blocks the policy write itself), and every admin call site threads a real CacheInvalidator.

2. (Blocking, fixed) resolve_cache_residency_zone() was always called with key_metadata=None, making the residency-zone cache-key component permanently "unknown" for vertex_ai/ollama keys regardless of their actual configured region - defeating the point of residency_zone being part of the cache key for those two providers. Fixed by introducing a single shared helper (_resolve_provider_key_metadata in common.py) used by both check_residency() and check_response_cache(), so the residency-zone cache-key component and the real enforcement decision are provably derived from the identical query, not two similar-but-divergent lookups.

3. (Blocking, fixed) Graceful degradation's substituted model was never re-validated against model-access policy, content-classification, or residency - a real RBAC self-escalation path. A Team Lead (lower trust than Org Admin) could configure their own team's degradation_policy.downgrade_target_model to a model their team's model-access policy otherwise denies, and it would be silently dispatched once the team's spend crossed the configured degradation threshold - with no error, no audit trail of a policy override. Fixed with two layers: (a) config-time validation (services/model_policy.py validate_downgrade_target_model, called from both the org- and team-scoped degradation_policy.py PUT handlers) rejects an unpermitted target model with 422 downgrade_target_model_not_allowed, no DB write; (b) request-time re-validation (revalidate_degraded_model in common.py) re-runs check_model_policy(), check_content_classification(), and check_residency() against the substituted model immediately before dispatch - closing the gap where policy is tightened after a degradation policy was originally configured under a more permissive state. On denial, the gateway implements the technical design's documented section 7.4 behavior exactly: skip degradation, fall through to the normal hard budget block for the original model (raise_hard_budget_block_after_degradation_skip) - never a silent fallback to an unauthorized model, and the resulting BudgetExhaustedError message contains only the caller's own name/budget/spend, never which model was denied or why (no cross-team policy-configuration leak). Verified via a real HTTP-level integration test (tests/integration/test_degradation_model_policy_revalidation_e2e.py) that PUTs a team model-restriction, then a degradation policy pointing at the now-disallowed model (422, no row persisted), and separately proves the request-time race case: degradation configured while policy is permissive, policy tightened afterward, next budget-proximity-triggered request correctly hard-blocks (402) rather than dispatching the now-denied model.

## Verified - no new issues found

- Provider key handling during health checks. refresh_single_provider_key_health() (services/provider_key_health.py) decrypts the real key via get_decrypted_provider_credential_from_row, then credential.to_secret_payload(), then validator.validate(secret_payload) - a genuine synthetic test HTTP call to the provider using a per-validator timeout (an active check, not something derived passively from live traffic) - then ValidationResult/map_http_status/map_httpx_exception (providers/base.py, confirmed to only ever produce static, templated messages, never echoing a raw provider response body), then ProviderKey.last_error/record_failure. No plaintext key material can reach a log line, an exception message, or the persisted last_error TEXT column at any point on this path. GET /v1/admin/provider-keys (ProviderKeyListItemResponse) and the existing GET /v1/admin/providers (ProviderKeyResponse) both have no ciphertext/nonce/auth_tag/plaintext-capable field defined on the schema at all - not just "current code doesn't populate one," the field doesn't exist to leak.
- Redis data exposure. The cache never stores anything a GET /v1/admin/cache/entries teaser response could leak beyond intended metadata - response_body is never included in the admin list response (confirmed by reading the actual dict construction in services/response_cache.py list_entries); only key_preview, team_id, user_id, provider, model, token counts, and timestamps are returned, matching AC4.3.9's "teaser, not full prompt" requirement. POST /v1/admin/cache/clear scopes correctly via scan_prefix using a UUID-typed team_id (no glob-injection surface since a UUID cannot contain wildcard characters), and its RBAC is inline-checked against the caller's real TeamMembership row, not a blindly-trusted role claim.
- RBAC boundaries on every new/changed admin endpoint this phase. Every team-scoped route (rate_limits.py, caching_settings.py, degradation_policy.py, failover_override.py, cache_admin.py team-scoped clear) uses require_team_role, which resolves the caller's actual TeamMembership row for the path's team_id - never trusts a bare role claim - and every team-scoped write forces team_id/scope_team_id from the URL path, never the request body. Org-Admin-only endpoints (backup_groups.py, providers.py, failover_events.py, degradation_events.py, the org-level rate_limits.py/caching_settings.py/degradation_policy.py routers, provider_key_health.py) correctly use router-level require_admin dependency, rejecting a plain Team Lead/Member session. This codebase remains single-org (DEFAULT_ORG_ID-scoped) throughout every Phase 4 addition, consistent with prior phases - no org-boundary regression.
- PUT /v1/admin/provider-keys/{id}/failover-config (new endpoint, added during the fix round - not covered by the original blocking findings, reviewed fresh): RBAC is Org-Admin-only via the same router-level dependency as every other route in that file. AC4.1.9's same-provider/same-model-support guard is real and enforced server-side (services/provider_keys.py set_failover_config rejects self-target and any cross-provider target with 422 failover_target_invalid, verified by tests/integration/test_failover_config_endpoint_e2e.py), not just a frontend-side dropdown filter. A maliciously- or carelessly-configured 2-key failover cycle cannot cause an unbounded retry loop: call_provider_with_failover's reactive retry is gated on selected.is_primary, meaning a retry can only ever fire off the true primary key, never off an already-selected backup - at most 2 provider-call attempts occur per request regardless of any configured cycle. The response schema has no secret-capable field.
- Audit trail integrity for Phase 4 events. FailoverEvent, RateLimitRejectionEvent, and DegradationEvent are all written synchronously from server-derived data only (key ids, timestamps, real provider-charged costs from provider_response.usage) - no field in any of these writes is sourced from unsanitized client input. CacheLookupEvent is the one deferred-via-BackgroundTasks write (stats-only, non-compliance-critical, consistent with the existing DLP async-log-only precedent from Phase 3).
- Secrets in the new admin API surface generally. label (provider-key creation) is a bounded, non-blank, non-secret string. keys on backup-group creation is confirmed to be a list of ProviderKey.label values only, never secret material. errors.py's redacted-field-names list already covers every secret-shaped field name Phase 4 could plausibly introduce - no new field name was found that should be on that list but isn't.
- Fix-6 warm-cache wiring (RateLimitCache/CachingSettingsCache/DegradationPolicyCache, added for the AC4.3.4 latency NFR, not a security requirement) introduces no security-relevant stale-read window: every admin PUT/DELETE for rate limits, caching settings, and degradation policy refreshes its cache synchronously, in-process, immediately after commit - the change takes effect on the very next request in a single-process deployment. Multi-process/multi-replica staleness is an inherent property of this whole process-local-cache architecture (shared with ModelPolicyCache/ResidencyRuleCache since Phase 3), not something Phase 4 introduces or worsens.

## Flagged, not blocking - needs follow-up or the deploying operator's attention

1. No automated test exercises the residency/DLP cache-invalidation wiring itself (Finding 1) end-to-end. Correctness was verified by direct code reading of every write path (all thread a real CacheInvalidator, all invalidate after commit, all fail open), but there is no Redis-gated integration test asserting that a tightened residency rule after a cache write actually causes the next request to miss/re-check. Recommend adding one (mirroring the shape of test_failover_config_endpoint_e2e.py) so a future refactor that accidentally drops a cache_invalidator argument is caught by CI, not the next security review.
2. Custom-DLP-pattern cache invalidation lives at the router layer (api/v1/admin/dlp_policy.py three handlers), not the service layer, unlike every other Finding-1 invalidation call site (which lives in the service function next to commit()). Functionally correct today, but a future new caller of create_custom_pattern/update_custom_pattern/delete_custom_pattern outside that one router file could forget the invalidation. Consider moving the cache_invalidator parameter into those three service functions for consistency - hardening, not required to ship.
3. Cache-clear (AC4.3.8) is a real SCAN+DEL, not the spec's "soft clear/sentinel value." services/response_cache.py's CacheInvalidator has no generation/sentinel mechanism to bump instead; this is a documented, intentional deviation with no security downside (actually stronger - no partially-stale sentinel state is possible), noted here for completeness against the literal AC text, not because it's a risk.
4. GET /v1/admin/provider-keys (and the failover-config endpoint) has no way to read back a key's current failover_enabled/failover_target_id state - the PUT response is the only place this information is ever returned; there's no persistent server-side read path for the admin console to display existing configuration across page reloads/sessions. This is a UX/completeness gap (the backend correctly enforces whatever was last configured; it just can't be displayed reliably after the fact), not a security exposure - flagged for a future backend follow-up (add these two fields to ProviderKeyListItemResponse), tracked in README's Known Limitations rather than blocking this review.
5. tokens_per_min rate limiting is configured/validated but not enforced on the live per-request path (services/rate_limit.py check_and_consume_rate_limit only checks requests_per_min). Assessed for a security/DoS angle specifically: this does not defeat the hard budget-exhaustion cutoff (check_budget_available still blocks the next request once spend crosses the ceiling - unchanged N-completes/N+1-blocked semantics from Phase 1.4), so a caller sending fewer, token-heavy requests to stay under an RPM limit is an availability/cost-shaping gap, not an unbounded-spend bypass. Non-blocking; already flagged to QA/architect as a functional gap independently.
6. Everything already flagged in the Phase 1.4-1.6 review (pricing-table live verification, a from-scratch docker-compose up pass on the operator's own machine, Vertex AI streaming-usage accuracy) remains an open operator-facing item, unchanged by this phase.

## Sign-off

PASS. All three original blocking findings (cache/residency/DLP boundary staleness, the dead residency_zone cache-key component for vertex_ai/ollama, and the degradation self-escalation path) are correctly and completely fixed, verified independently by direct code reading of every call site and by running the relevant tests - not by trusting the implementing agent's self-report. The new PUT /v1/admin/provider-keys/{id}/failover-config endpoint (added during the fix round) correctly enforces Org-Admin-only RBAC, has real server-side same-provider validation, and is structurally incapable of an unbounded failover loop even under a maliciously-configured cycle. Test baseline reproduced independently: 656 passed/1 skipped (unit), 159 passed/3 skipped (integration) - all skips are Redis-gated tests correctly self-skipping in an environment without a default Redis instance; a full docker-compose rebuild (profiles cache + sso, up --build) was run against this exact code afterward and confirmed all 5 containers (postgres, redis, keycloak, backend, frontend) recreated fresh and healthy, with a live smoke test against /v1/admin/rate-limit-rules, /v1/admin/backup-groups, /v1/admin/provider-keys, and /v1/admin/usage/summary all returning 200 with the expected Phase 4 fields present. Phase 4 is approved to ship, contingent only on the non-blocking follow-ups above being tracked (items 1 and 4 are the most worth prioritizing next), none of which are re-review gates.
